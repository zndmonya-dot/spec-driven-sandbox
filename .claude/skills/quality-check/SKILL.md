# 品質チェックリスト

上から順に確かめる。1つでも満たさなければ、直してから最初に戻る。
最後に、各項目の結果を PR 本文の「品質チェック」に貼る。

## 機械で確かめる

- [ ] `npm run verify` が通る（guard → lint → 型検査 → 仕様のテスト）

`npm run guard` は、テストのスキップ（`@skip` などのタグ、`.skip` / `.only`）が紛れ込んでいたら落ちる。

## 目で確かめる

- [ ] **仕様が注文書どおり**：`specs/` のシナリオが注文書の「決まりごと」と同じ。実装に合わせて書き換えていない
- [ ] **赤から始めた**：仕様を写したコミットの時点でテストが不合格だった（コミット履歴で示せる）
- [ ] **言葉**：新しい言葉は `CONTEXT.md` に足してある。コードと仕様は `CONTEXT.md` の言葉だけを使っている
- [ ] **判断の記録**：注文書に書いていなかったことを AI が決めたら、PR 本文の「AI が判断したこと」に書いた。後から変えにくい判断は `docs/adr/` にも残した
- [ ] **やらないこと**：注文書の「やらないこと」に入っているものを作っていない
- [ ] **差分が小さい**：注文に関係ないファイルの変更や、ついでの整理を混ぜていない
